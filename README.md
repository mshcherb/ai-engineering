# Stock Opinion Extractor

Курсовий проєкт AI Engineering (robot_dreams, 2 потік).

Сервіс витягує структуровані дані з «брудних» текстів інвесторських чатів і форумів (Telegram, Reddit): які компанії згадуються, яке ставлення автора (bullish / bearish / neutral / mixed), аргумент, цільова ціна, горизонт і цитата-доказ. Порівнює провайдерську модель (OpenRouter) з локальною (Ollama).

Кейс 1 — **Structured Extraction Service**.

## Запуск

Потрібно: Docker + Docker Compose, `make`, ключ [OpenRouter](https://openrouter.ai/).

```bash
cp .env.example .env        # вписати OPENROUTER_API_KEY
make run                    # підняти контейнери і прогнати всі тексти
```

Результат — файл `results/<час>_<конфіг>_<версія промпту>.jsonl`.

Інші команди:

```bash
make run-sample             # швидка перевірка на 3 текстах
make run ARGS="--run llama32_3b_t0 --prompt v2 --limit 10"
make eval                   # оцінити останні прогони на golden set -> results/metrics.md
make compare                # прогнати всі конфіги і оцінити (локальна модель ~1 год на конфіг)
make check                  # перевірити, що OpenRouter і Ollama відповідають
make down
```

Локальна модель для кроку 2 (один раз):

```bash
docker compose exec ollama ollama pull llama3.2:3b
```

```

```

## Схема

Одна картка на текст:

| поле | тип |
|---|---|
| `language` | enum: uk / ru / en / mixed / unknown |
| `is_about_stocks` | bool |
| `mentions[]` | список згадок, кожна: `company`, `ticker`, `asset_type` (enum), `sentiment` (enum), `reasoning`, `price_target`, `horizon` (enum), `quote` |
| `summary` | одне речення |

Автор, дата і джерело не запитуються в моделі — вони беруться з даних.

## Дані

- **Telegram:** 2 інвестиційні канали за 11–20.10.2026 (експорт Telegram Desktop).
- **Reddit:** r/stocks та r/investing, top за тиждень 13–20.10.2026.

Сирі експорти з нікнеймами в репозиторій не потрапляють. `scripts/build_dataset.py` відбирає різноманітні тексти (з тикерами, компанії словами, ринок без компаній, шум; короткі / середні / довгі) і знеособлює їх: посилання → `<URL>`, `@нік` / `u/нік` → `<USER>`, повідомлення з іменами виключені.

## Моделі та конфігурації

| конфіг | модель | temperature / top_p |
|---|---|---|
| `gpt4o_mini_t0` | `openai/gpt-4o-mini` (OpenRouter) | 0.0 / 1.0 |
| `gpt4o_mini_t07` | `openai/gpt-4o-mini` (OpenRouter) | 0.7 / 0.9 |
| `llama32_3b_t0` | `llama3.2:3b` (Ollama, CPU) | 0.0 / 1.0 |
| `llama32_3b_t07` | `llama3.2:3b` (Ollama, CPU) | 0.7 / 0.9 |

Обидві моделі йдуть через один `LLMClient` — різняться лише `base_url`, ключ і назва моделі. Для Ollama таймаут 300 с (CPU, ~10 токенів/с).

## Метрики (`make eval`)

- **% valid** — частка відповідей, що пройшли схему; **latency p50 / p95**; **$ / 1000 документів** (з `usage.cost` OpenRouter; локальна модель — $0 за API).
- **Точність на golden set:** `is_about_stocks`, `language`; для згадок — precision / recall / F1 (зіставлення за тикером або назвою); для зіставлених згадок — `sentiment`, `asset_type`, `horizon`, `price_target`.
- Невалідна відповідь рахується як помилка в усіх полях.
- `results/errors.md` — кожна розбіжність з golden set (матеріал для аналізу помилок).

## Кожен запис результату

`id`, `model`, `provider`, `prompt_version`, `temperature`, `top_p`, `status`, `latency_s`, `attempts`, `tokens_in`, `tokens_out`, `cost_usd`, `output` (картка), `error`, `repair_reason`, `raw` (сирий вихід, якщо невалідний).

Статуси:
- `ok` — валідна картка з першої спроби;
- `repaired` — перша відповідь не пройшла валідацію, модель отримала список помилок і виправила (одна спроба);
- `failed` — невалідна й після виправлення;
- `error` — відповіді немає (мережа, таймаут, `deadline_s`).

Валідація = JSON Schema (structured output) + перевірки, яких схема не виражає (формат тикера: `NVDA`, `BRK.B` або `null`, а не рядок `"null"` чи `$tsla`).

`prompts/v1.md`, `prompts/v2.md` — версія й дата у front matter, що й чому змінено — у `prompts/CHANGELOG.md`. Версія за замовчуванням — `prompt_version` у `config.yaml`, інша — `--prompt v2`.

# ДЗ2: RAG по звітності компаній

Друга частина проєкту. Агент у блоці 3 перевірятиме думки з чатів (ДЗ1) за фактами, тому корпусом стала **публічна звітність компаній, які найчастіше згадувались у постах**: банки (JPM, GS, BAC, C, WFC), напівпровідники (NVDA, MU, TXN, ASML, TSM), TSLA, AMZN.

```bash
make corpus     # завантажити документи з SEC EDGAR (потрібен SEC_USER_AGENT у .env)
make ingest     # документи -> data/corpus/chunks.jsonl
```

## Корпус

32 документи, 2 формати (`data/corpus/manifest.csv` — джерело, дата, sha256 кожного файлу):

| що | формат | скільки |
|---|---|---|
| річні звіти 10-K / 20-F | HTML (SEC EDGAR) | 14 |
| пресрелізи з квартальними результатами (8-K, exhibit 99.1) | HTML (SEC EDGAR) | 14 |
| квартальний management report, earnings release, презентація TSMC | PDF (сайт TSMC) | 4 |

- **Пастки «застаріла версія»** закладені свідомо: 10-K JPM і GS за 2024 і 2025 роки; пресрелізи JPM, GS, BAC, C і звіт TSMC за Q2 і Q3 2026. Кожен чанк має `latest: true/false`.
- **Пастки «схожі документи»** виникають самі: п'ять банків мають однакову структуру звітів і однакові назви метрик.
- Сирі файли (143 МБ) у git не потрапляють: `scripts/fetch_corpus.py` завантажує їх заново, а sha256 у manifest гарантує, що це ті самі файли. PDF TSMC сайт не дає скачати скриптом, тому вони зберігаються вручну за посиланнями з `data/corpus/sources.yaml`.
- Розшифровки earnings call (LSEG) **не використовуються**: їхня ліцензія забороняє поширення, а повний текст чанків лежить у публічному репозиторії.
- Персональних даних немає: це публічні звіти компаній.

## Ingestion (`rag/extract.py`, `rag/ingest.py`)

На основі практики заняття 6, адаптовано під SEC-звіти:

- **Витягування зі структурою.** HTML з EDGAR — це inline XBRL без `<h1>`/`<h2>`: заголовки розпізнаються за жирним шрифтом в inline-стилях і за шаблоном `Item 7.` (розділи 10-K). Таблиці перетворюються на markdown-таблиці, причому `$ | 1,234` і `(12 | )` склеюються в одну клітинку. Приховані XBRL-факти (`ix:header`) викидаються. PDF: текст по сторінках, номер сторінки зберігається для цитування.
- **Очищення.** NFKC, невидимі символи, зайві пробіли. У PDF прибираються колонтитули (рядки, що повторюються на більшості сторінок, з точністю до номера сторінки) і перенесені рядки. Абзаци, розірвані на кілька блоків (розрив сторінки або брошура, сконвертована в HTML, як річний звіт ASML), склеюються.
- **Дедуплікація.** Документи — за sha256 нормалізованого тексту. Майже-дублікати шукаються за Jaccard по 5-словних шинглах: 10-K 2024 і 2025 збігаються на 51% (JPM) і 59% (GS). Їх **не видаляємо**: це версії, потрібні для пасток, тож вони лише позначаються `latest`. Чанки — за sha256 тексту: 220 однакових чанків (дисклеймери, що повторюються з кварталу в квартал) залишені лише в найновішій версії.

## Chunking: чому так

**По розділах, до 400 токенів, без розрізання абзаців і рядків таблиць.**

- Звітність — це розділи з власними заголовками («Item 1A. Risk Factors > Credit Risk»). Питання майже завжди стосується одного розділу, тому чанк не перетинає межу розділу і знає свій шлях `section`. Це потрібно і для цитування («документ + розділ»), і для фільтрів.
- **Таблиці** — головне джерело цифр (виручка, маржа, CET1). Таблиця не ріжеться посередині рядка. Довга таблиця ділиться між рядками, і кожна частина отримує копію шапки, тож цифра в чанку завжди лишається з назвою своєї колонки.
- **400 токенів**, бо embedding-модель (`bge-small-en-v1.5`) читає максимум 512 своїх токенів, а її токенізатор ріже числа дрібніше, ніж tiktoken. Чанк більшого розміру модель просто обрізала б. Менше за 60 токенів чанк не буває: короткий шматок приєднується до наступного блоку того самого розділу.

**Порівняння з фіксованим вікном** (400 токенів, overlap 50) на всіх 32 документах (`data/corpus/ingest_report.json`):

| | по розділах | фіксоване вікно |
|---|---|---|
| чанків | 9 694 | 7 857 |
| середній розмір, токенів | 279 | 399 |
| чанк починається посеред речення | 3.1% | 9.6% |
| чанк розрізає рядок таблиці | 0.9% | 46.0% |
| у чанка відомий розділ | 98.5% | 0% |

Ціна підходу: чанків на 23% більше, а частина з них менша за ліміт. Чи окупається це якістю пошуку, перевіримо на кроці 2 (recall@k для обох варіантів).

**Відомі обмеження:** брошура ASML дає більшість чанків, що починаються посеред речення (вона зверстана як PDF, кожен рядок окремим блоком). Слова, розбиті на кілька `<span>`, іноді отримують зайвий пробіл («expo rted»).

Кожен чанк (`data/corpus/chunks.jsonl`): `chunk_id`, `doc_id`, `ticker`, `company`, `kind`, `form`, `period`, `filed`, `latest`, `title`, `section`, `page`, `url`, `format`, `doc_hash`, `chunk_hash`, `chunk_index`, `n_tokens`, `text`, `pipeline_version`, `ingested_at`.

## Пошук (`rag/index.py`, `rag/search.py`)

```bash
make index            # embeddings (кеш data/corpus/embeddings.npz, перший запуск ~25 хв на CPU)
make eval-retrieval   # recall@k / MRR -> evals/results/retrieval.md
```

- **Embeddings:** локальна `BAAI/bge-small-en-v1.5` (fastembed, 384 виміри, вікно 512 токенів), безкоштовно і без ключа. Перед текстом чанка — контекстний заголовок «компанія, документ, період, розділ»: абзаци п'яти банків майже однакові, і без заголовка вектор не знає, чий це текст. Кеш векторів (float16, ~7 МБ) комітиться, тож CI і свіжий клон не перераховують корпус.
- **Векторна база:** Qdrant (in-process), payload з метаданими чанка.
- **Hybrid:** BM25 + векторний пошук по 30 кандидатів, об'єднання через Reciprocal Rank Fusion (k = 60).
- **Reranking:** cross-encoder `Xenova/ms-marco-MiniLM-L-6-v2` пересортовує 30 кандидатів hybrid.
- **Фільтри:** `ticker`, `kind` (річний звіт / пресреліз / …), `latest` (лише остання версія документа), `period_from` / `period_to`.

**Якість пошуку** (`evals/retrieval_questions.jsonl`: 20 питань, з них 18 з відповіддю в корпусі і 2 без неї — їх оцінюємо вже на відповідях, «не знаю»; пошук ведемо за еталонним англійським формулюванням; релевантний чанк = з потрібного документа і містить рядок-доказ):

| chunking | режим | recall@5 | recall@10 | MRR@10 | p50, с |
|---|---|---|---|---|---|
| по розділах | vector | 0.61 | 0.72 | 0.50 | 0.1 |
| по розділах | bm25 | 0.61 | 0.72 | 0.53 | 0.02 |
| по розділах | hybrid | 0.67 | 0.89 | 0.54 | 0.15 |
| по розділах | **hybrid + rerank** | **1.00** | **1.00** | **0.81** | 2.7 |
| фіксоване вікно | vector | 0.83 | 1.00 | 0.66 | 0.1 |
| фіксоване вікно | hybrid | 0.83 | 0.89 | 0.64 | 0.12 |
| фіксоване вікно | hybrid + rerank | 0.89 | 1.00 | 0.79 | 2.8 |

Повна таблиця (усі варіанти запиту × режими × chunking) — `evals/results/retrieval.md`.

- **Reranking дає найбільший приріст:** MRR 0.54 → 0.81, усі 18 правильних чанків у топ-5. Ціна — ~2.5 с на запит на CPU.
- **Чесний мінус розбиття по розділах:** чистий векторний пошук на фіксованих вікнах кращий (recall@5 0.83 проти 0.61). Ймовірна причина: фіксовані чанки довші (400 токенів проти 279 у середньому) і перекриваються, тож у вектор потрапляє більше контексту навколо цифри. Після reranking розбиття по розділах краще (1.00 проти 0.89), а для цитування «документ + розділ» воно потрібне. Тому лишаємо його.
- **Фільтр за тикером майже нічого не змінює:** контекстний заголовок уже відрізняє банки один від одного.
- На 18 питаннях одне питання — це ~6 п.п., тож різниця менша за 10 п.п. в межах шуму.

### Query rewriting: російське питання → англійський запит (`rag/rewrite.py`)

Корпус, embedding-модель (bge-small-**en**) і BM25 — англійські, а питання користувача — російською. Тому перед пошуком gpt-4o-mini (OpenRouter, t = 0, structured output) переписує питання в `{query_en, tickers, period}`. Промпт — `prompts/rewrite_v1.md` (список компаній корпусу з тикерами підставляється з `chunks.jsonl`), changelog — `prompts/CHANGELOG.md`.

- `query_en` — питання так, як його сформулював би звіт: офіційна назва компанії, стандартна назва метрики, період словами.
- `tickers` → фільтр `ticker`. `period` (рік / квартал / fiscal) код, а не модель, перетворює на діапазон дат: Q3 2026 → `period` від 2026-09-30 до +75 днів (пресрелізи виходять за 2–6 тижнів після кварталу, а реліз за Q2 від 14.07 у вікно Q3 не потрапляє). Fiscal-періоди й прогнози — без фільтра за датою: фінансові роки компаній різні (у NVIDIA Q2 FY2027 — травень–липень 2026).
- Відповіді кешуються в `evals/rewrite_cache.jsonl` (ключ — версія промпту + модель + питання): повторний прогін безкоштовний і дає ті самі запити. Вартість ≈ **$0.12 на 1000 питань**.

Порівняння варіантів запиту (18 питань з відповіддю, k = 10):

| запит | chunking | vector R@5 | hybrid R@5 | hybrid + rerank R@5 | hybrid + rerank MRR |
|---|---|---|---|---|---|
| RU як є | по розділах | 0.00 | 0.00 | 0.06 | 0.06 |
| RU → EN (LLM) | по розділах | 0.72 | 0.61 | 0.89 | 0.69 |
| **RU → EN + фільтри LLM** | **по розділах** | 0.78 | 0.78 | **1.00** | **0.76** |
| EN еталон | по розділах | 0.61 | 0.67 | 1.00 | 0.81 |
| EN + фільтр тикера (еталон) | по розділах | 0.61 | 0.67 | 1.00 | 0.81 |
| RU як є | фіксоване вікно | 0.22 | 0.22 | 0.00 | 0.01 |
| RU → EN (LLM) | фіксоване вікно | 0.83 | 0.67 | 0.89 | 0.73 |
| RU → EN + фільтри LLM | фіксоване вікно | 0.83 | 0.83 | 0.94 | 0.82 |
| EN еталон | фіксоване вікно | 0.83 | 0.83 | 0.89 | 0.79 |

- **Без перекладу пошук не працює:** російське питання знаходить правильний чанк у 0–1 випадку з 18. Англійська модель бачить кирилицю як шум, а BM25 не знаходить спільних слів.
- **Переклад повертає майже все:** hybrid + rerank 0.06 → 0.89. Два промахи (r02, r06) — правильний документ у топі, але не той чанк: модель пише «net revenues», а у звіті «reported revenue», і таких чанків у пресрелізі багато.
- **Фільтри від LLM закривають різницю:** з тикером і періодом — 1.00, як в еталоні. Тут фільтр корисніший, ніж для еталонного EN, бо відсікає сусідній квартал (пастки r01 / r02). Тикери правильні в 18/18, фільтри ніде не викидають правильний чанк (18/18) — по кожному питанню в `evals/results/retrieval.md`.
- MRR трохи нижчий за еталон (0.76 проти 0.81): машинний переклад менш точний у термінах, ніж ручний.
- **Знайдена помилка перекладу:** r16 «Киберкаб» → «Cybertruck» (це інший продукт). Пошук не постраждав завдяки фільтрам, але на кроці 3 така заміна може зіпсувати відповідь.
- **Спроба виправити промптом (rewrite_v2) відхилена:** правило «назви продуктів транслітерувати, не підміняти» не виправило r16, зате зламало r13 (прогноз на Q4 отримав фільтр Q4 і втратив звіт за Q3): recall@5 1.00 → 0.94, MRR 0.76 → 0.69. Лишаємо v1. Висновок: правку промпту перевіряємо на всьому наборі, не лише на питанні, під яке її робили. Надійніше виправити в коді на кроці 3: якщо з фільтром періоду нічого не знайдено — повторити без нього; відповідна модель отримує оригінальне російське питання.

## Відповідь з джерелами (`rag/answer.py`)

```bash
make ask Q="Какая грос маргин TSMC в третьем квартале 2026 года?"
make answers-sample   # 20 питань -> evals/results/answers_sample_<prompt>.md, для ручного перегляду
```

```
Гросс маржа TSMC в третьем квартале 2026 года составила 66.4% [S1].

Источники:
[S1] TSM PDF quarterly management report, period 2026-09-30 · Section: Financial Highlights · p. 1
      https://investor.tsmc.com/...
```

Конвеєр: питання → rewrite (`query_en` + фільтри) → hybrid + rerank, k = 8 → контекст у межах бюджету → gpt-4o-mini (t = 0, structured output `{found, answer, citations}`) → перевірка цитат у коді.

- **Тільки знайдені чанки.** Кожен чанк у промпті має мітку `[S1]` і заголовок «компанія, форма, період, розділ, сторінка». Відповідь — російською, мітка після кожного речення з фактом; у кінці список джерел: документ, розділ, посилання на оригінал.
- **Цитати перевіряє код, а не модель:** мітки джерел, яких модель не отримувала, видаляються (`invalid`); `found` = модель сказала, що відповідь є, **і** в тексті є хоча б одна справжня мітка; речення з числом без мітки рахуються як `uncited_claims`.
- **Бюджет токенів:** ≤ 3000 токенів джерел (tiktoken `o200k_base`, токенізатор gpt-4o). Чанки йдуть від найкращого за reranker; той, що не влазить, пропускається, коротший нижче ще може влізти. На 20 питаннях — 1700–2900 токенів контексту.
- **«Не знаю»** у трьох місцях: (1) пошук нічого не знайшов (наприклад, Apple — тикера `AAPL` у корпусі немає, модель навіть не викликається); (2) модель повернула `found: false` — тоді показуємо фіксоване «В документах этого нет.» і її пояснення, чого бракує; (3) модель сказала `found: true`, але не поставила жодної справжньої мітки — відповідь без джерела не показуємо.
- **Страховка для фільтра періоду:** якщо з фільтром періоду нічого не знайдено, повторюємо пошук з одним тикером (`period_dropped`). Так питання «Q3 2026 ASML» все одно отримує річний звіт ASML, а модель має сама сказати, що даних за Q3 там немає (r20 — так і є).
- **Моделі відповіді дається оригінальне російське питання**, а не `query_en`: слова користувача важливіші за переклад (r16: rewrite переклав «Киберкаб» як Cybertruck, а відповідь — про Cybercab, бо так у джерелі й у питанні).
- Вартість: ≈ $0.6 на 1000 питань (rewrite + відповідь, gpt-4o-mini через OpenRouter), ~4 с на питання (з них ~2.5 с — reranker на CPU).

**Промпти:** `prompts/answer_v1.md` → `answer_v2.md` (за замовчуванням), changelog — `prompts/CHANGELOG.md`. Прогін 20 питань пошукового тестсету (18 з відповіддю + 2 без):

| | v1 | v2 |
|---|---|---|
| відповідь знайдена (з 18) | 17 | **18** |
| «не знаю» там, де відповіді немає (з 2) | 2 | 2 |
| речення з фактом без мітки | 1 (r16) | 1 (r16) |

Помилки v1, виправлені у v2: r03 (рядок розплющеної таблиці `CET1 Capital Ratios 3 Std. 13.9%` модель не впізнала як відповідь), r04 («$ 18,679 млн» замість $18.68 млрд: правило v1 «$50.2 billion → $50,2 млрд» змішало англійські й російські роздільники). Відповіді обох версій — `evals/results/answers_sample_answer_v1.md` і `..._v2.md`. Повна оцінка якості відповідей (тестсет ≥ 20, judge, faithfulness) — крок 4.

**Відомі обмеження:**
- **Формат чисел.** Джерела англійські (`$6,055` у таблиці «In millions»), відповідь російська: модель часом пише «$6,055 миллиарда» — по-російськи це 6.055 млрд (вірно), по-англійськи — у тисячу разів більше. Детермінований скорер на кроці 4 має нормалізувати числа, а не порівнювати рядки.
- **Одна мітка на кілька речень** (r16): gpt-4o-mini не завжди повторює мітку, хоч промпт цього вимагає. Код це ловить (`uncited_claims`), але не виправляє.

## Тестсет і evals у CI

```bash
make lint-testset    # перевірка тестсету на корпусі: документи, рядки-докази, числа з must
make eval-answers    # 29 питань через RAG -> evals/results/answers.{jsonl,json,md}; ARGS=--rescore — без нових викликів
make eval-ci         # те саме, що CI: lint + відповіді + LLM-judge + gate (evals/baseline.json)
make calibrate       # judge проти ручної розмітки evals/labels.jsonl -> evals/results/calibration_*.md
```

- **Тестсет** `evals/testset.jsonl`: 29 питань — 8 фактів, 8 пасток «застаріла версія», 6 «схожі документи», 2 без чисел, 5 без відповіді в корпусі. У кожного — еталон російською, ключові числа `must`, правильні документи. Перевіряє людина (`reviewed`), `evals/testset.py` (lint) перевіряє, що все це справді є в корпусі.
- **Детерміновані скорери** (`evals/answer_eval.py`, `evals/scoring.py`): правильне джерело серед цитат, ключові числа (порівняння за значенням, а не рядком: «$5,951 миллиона» = «$6.0 billion», «66.4%» ≠ «67.7%»), «не знаю» де треба і хибне «не знаю».
- **LLM-judge** (`evals/judge.py`, claude-haiku-5.5): `judge_correct` — відповідь проти еталону; `grounded` (faithfulness) — кожне твердження відповіді проти процитованих чанків. Відкалібровано на 18 ручних оцінках: згода 1.00 і 0.87–0.93, жодного false pass. Чому haiku, а не gpt-4o-mini, — `prompts/CHANGELOG.md`.
- **CI** `.github/workflows/evals.yml`: на кожен push / PR, падає нижче порогів з `evals/baseline.json`. Потрібен секрет `OPENROUTER_API_KEY` (Settings → Secrets and variables → Actions). Моделі fastembed кешуються, вектори чанків і rewrite-кеш лежать у git, тож прогін ≈ 5 хв і ≈ $0.03.

Результати, калібрування і розбір помилок — у [`REPORT.md`](REPORT.md).
